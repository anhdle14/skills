## Harness bug found by the backfill

Human-only skills never auto-trigger, so a positive case could never pass. The runner now injects their `SKILL.md` the way `/skill:name` does and skips the trigger assertion. The first version of that injection passed the raw file, which starts with `---`, so `pi` parsed the prompt as a CLI flag and exited 1 - all three `autoresearch` cases failed with `pi exited 1`. `human_only_prompt()` now strips the frontmatter, and two unit tests pin the behavior (25 tests total, passing).

## The `research` refactor: what the evidence allowed

Hunting for an over-trigger failure produced two hits:

```
hunt-add-flag    [enabled]: 0/1 passed   FAIL trigger=True, want False
hunt-tech-choice [enabled]: 0/1 passed   FAIL trigger=True, want False
```

Both were **my cases being wrong, not the skill**. `research` states outright that "a todo list, single-function utility, or config change still needs a short design", and a Postgres-vs-SQLite question is exactly the trade-off work it exists for. So loading on those prompts is the intended contract. They are now positive cases (`small-scoped-change`, `technology-trade-off`) that pin that contract, and the description was left alone - no observed failure, no change.

What the evidence did support was pruning duplication: the no-implementation gate was stated three times (hard-gate blockquote, checklist step 9, closing paragraph of "After the Design"). Now stated once in the blockquote, with the other two reduced to plain hand-off lines. Full suite re-run after the edit: 10/10.
